# space-invaders

A faithful browser clone of the 1978 arcade game. Open a page, play, no install
and no account. Vanilla TypeScript on a 2D canvas, built with Vite, published to
GitHub Pages.

**Live:** https://jdonaghy.github.io/space-invaders/

## Where this came from — read this before changing scope

This repo exists because a customer asked for it through the intake portal and
**approved a specific design**. The approved scope is reproduced in full below.
It is not a wishlist and not a starting point for your own ideas: a change that
adds something the customer did not ask for is as wrong as one that drops
something they did.

> **What the customer approved**
>
> A web page you can open in a browser and play Space Invaders on — no install,
> no account, nothing to sign up for. Rows of aliens march side to side and drop
> toward you; you move a cannon along the bottom and shoot; the wave speeds up
> as you clear it. Four shields wear away where they are hit. Three lives, then
> game over. It works with a keyboard on a computer and with your thumbs on a
> phone, and it remembers your best score on that device.
>
> "Simple" was read as **faithful to the arcade rather than feature-rich**: one
> alien formation that repeats faster each wave, one kind of shot, no power-ups,
> no accounts and no online leaderboard.

**Explicitly out of scope** — do not add these, even if they seem like obvious
improvements. Each was shown to the customer as excluded and approved that way:

- Accounts, sign-in, or an **online** leaderboard (a local best score is in)
- Power-ups, extra weapons, or new enemy types
- Two-player
- Anything that is not a web page (no app-store build, no packaging)

If a task genuinely cannot be done inside that scope, say so in your final
message rather than widening it.

## The one architectural decision

**A hand-written game loop on a plain 2D canvas. No game engine, no framework,
no physics library.** The whole game is a few hundred lines of TypeScript:
`requestAnimationFrame`, a fixed-timestep update, and `CanvasRenderingContext2D`
draw calls. Do not add Phaser, three.js, Pixi, React, or a state-management
library — reaching for one is the single most likely way to get a change
rejected here.

Sprites are pixel grids drawn as filled rects, the way the original was a bitmap.
Keep them as data (a string or array per sprite), not as image files.

## Rules for workers

- **Stay faithful to the arcade.** When a detail is ambiguous, the 1978 original
  is the tiebreaker: one player shot in flight at a time, the formation steps
  rather than glides, the march tempo rises as the wave thins, a cleared wave
  restarts lower and faster.
- **It must work on a phone.** Touch controls and a layout that survives portrait
  and landscape are requirements, not polish. Test at a narrow viewport before
  calling something done.
- **No dependencies without the operator saying so.** `package.json` should stay
  at Vite + TypeScript. A PR that adds a runtime dependency needs to justify it
  in the PR body.
- **Commit and push before your final message** — even if the build is broken or
  you ran out of time. Uncommitted work is destroyed when the session ends.
- **`gh` is on the deny-list.** The coordinator owns all GitHub interaction; use
  plain `git`.
- **Only the coordinator writes docs.** Do not edit this file or `README.md`.

## Testing — the toy exemption

**This repo is exempt from claude-coordinator's black-box acceptance bar**, the
same way `stick-demo` is. There is no sealed acceptance suite, no Playwright
harness, and the adversarial reviewer should not request one. The exemption is
deliberate: the dogfood this repo belongs to is measuring whether plain-language
intake becomes a decomposition an engineer accepts, not this game's test
coverage.

What still applies:

- **`npm run build` must exit 0.** That is `tsc && vite build`, so a type error
  is a build failure. It is the Test stage's whole gate here — verify it by exit
  code, not by reading output.
- **Smoke it yourself in a browser** before your final message, and say in that
  message what you actually observed on screen. "It compiles" is not "it plays".
- Small unit tests for pure logic (collision maths, the march-tempo curve, score
  tables) are welcome but never required.

## Commands

```bash
npm ci          # install
npm run dev     # local dev server
npm run build   # tsc && vite build — the Test stage's gate
npm run preview # serve the built bundle
```

## Deploy

Merging to `main` builds and publishes to GitHub Pages automatically. The
workflow also runs on every pull request — build verification only, no deploy.
That `pull_request` trigger is load-bearing: a workflow that fires only on `main`
leaves every PR with zero reported checks, and the coordinator's merge gate then
refuses to merge any of them.
